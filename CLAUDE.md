# Проект: Telegram-бот для риелторов (генерация объявлений)

## Что делает бот

Одна функция: пользователь присылает ссылку на Яндекс.Карты + отвечает на вопросы
о квартире (через кнопки и текст) → бот сам изучает район вокруг адреса → генерирует
готовый текст объявления через LLM.

Это первый показательный проект (портфолио) для риелторов — цель: минимальная
стоимость эксплуатации (в идеале около нуля), максимально быстрый запуск,
работает пока только по Москве.

## Стек

- **Язык/фреймворк:** Python 3.12+, aiogram 3.x
- **FSM:** aiogram StatesGroup, хранилище — MemoryStorage (без Redis на MVP)
- **Геокодинг:** Яндекс Geocoder API (только адрес по координатам, бесплатный лимит)
- **Поиск объектов рядом (POI):** Overpass API / OpenStreetMap — бесплатно
- **LLM:** GigaChat API, модель `GigaChat` (Lite). Freemium-лимит для физлиц — по
  официальным тарифам 250M токенов на Lite (плюс отдельные пулы на Pro/Max/Ultra),
  лимит на 12 месяцев, а не помесячно (в начале проекта ошибочно считали 1M/мес —
  поправлено после регистрации и сверки с developers.sber.ru/docs/ru/gigachat/tariffs).
- **Хостинг:** VPS (Selectel), Docker + docker-compose
- **Запуск бота:** long polling (НЕ webhook — не нужен домен/SSL для MVP)
- **Telegram API — через Cloudflare Worker-прокси, не напрямую.** На проде сеть
  Selectel режет маршрут до IP Telegram (`149.154.160.0/20` и соседние) — трассировка
  обрывается на 2-3 хопе внутри сети провайдера, при этом остальной интернет с того
  же сервера работает нормально. Обходим через бесплатный Cloudflare Worker
  (`TG_API_BASE_URL` в `.env`, код воркера — простой reverse-proxy на `fetch`,
  переписывает хост в `api.telegram.org` и пересылает путь/тело как есть). Если
  переносить бота на другой VPS без этой блокировки — просто оставить
  `TG_API_BASE_URL` пустым, код автоматически идёт напрямую в Telegram.

## Ключевые архитектурные решения (и почему)

- **Geocoder ≠ Search API.** Яндекс Geocoder используется ТОЛЬКО чтобы превратить
  координаты в адрес. Он не ищет метро/школы — для этого отдельный сервис.
- **POI — через Overpass, не через Яндекс Search API.** Яндекс API Поиска по
  организациям платный без бесплатного тарифа (от ~20 800 ₽/мес даже на минимальном
  лимите) — не подходит для проекта с нулевым бюджетом. Overpass/OSM бесплатен,
  и для Москвы (в отличие от небольших городов) данные достаточно полные.
- **LLM — GigaChat, не Claude/OpenAI.** На старте используем бесплатные лимиты
  российских моделей. GigaChat даёт 1M токенов/мес бесплатно физлицу — с запасом
  хватает на сотни генераций в месяц.
- **Скрапинг Яндекс.Карт — не делаем.** Рассматривали идею парсинга карт напрямую
  (раз бот работает только по Москве), но это нарушает пользовательское соглашение
  Яндекс.Карт — оставлено как возможный план Б на будущее, не часть MVP.
- **ИИ-агент для сбора новостей о районе (стройки и т.д.) — НЕ делаем в MVP.**
  Рассматривали и отклонили: риск недостоверной/устаревшей информации в
  фактическом (не просто стилистическом) контексте — может навредить репутации
  риелтора. Возможная идея для V2, и то с обязательным указанием источника.
- **Лимит GigaChat исчерпан → ждём, не переходим на платный тариф.** При
  исчерпании бесплатного лимита бот отвечает "сервис временно недоступен,
  попробуйте позже" и не генерирует объявление. Автооплата или fallback-шаблон
  без LLM не делаем в MVP — сохраняем цель нулевой стоимости эксплуатации.
- **Адрес вне Москвы → жёсткий отказ.** Если Geocoder вернул адрес не по
  Москве, бот сообщает "Бот пока работает только по Москве" и не продолжает
  сценарий (без пометки "продолжить с оговоркой").
- **Сбой Geocoder/Overpass → retry + кнопка "Повторить".** Автоматический
  retry 1-2 раза; при повторной неудаче — сообщение об ошибке с кнопкой
  "Повторить", пользователь не теряет прогресс анкеты (не начинает заново).
- **Rate limiting на генерации — НЕ делаем в MVP.** Аудитория пока небольшая
  и доверенная (первый показательный проект), риск спалить общий лимит
  GigaChat расценили как приемлемый. Вернуться к вопросу при росте аудитории.
- **Тулинг — requirements.txt + venv, без Poetry/uv.** Минимум зависимостей
  и лишних инструментов на старте, укладывается в Docker без доп. слоёв.
- **Деплой — вручную по SSH, без CI.** `git pull` + `docker-compose up -d`
  на VPS руками; автодеплой через GitHub Actions отложен — редкие деплои на
  MVP не оправдывают настройку секретов/доступа CI к VPS.
- **Логирование — stdlib logging в stdout.** docker logs достаточно для
  отладки на одной VPS; файловый лог с ротацией и внешние сервисы (Sentry)
  избыточны для нулевого бюджета.
- **POI-набор на MVP — только минимум из сценария.** Метро/транспорт и
  школы/садики в радиусе 500-800м, без парков/магазинов/фитнес-клубов —
  расширение набора отложено на V2.
- **Overpass-теги (закрывает открытый вопрос ниже):** метро —
  `railway=station`+`station=subway`; школа — `amenity=school`; садик —
  `amenity=kindergarten`. Радиус — единый `800m` для всех трёх категорий
  (верхняя граница диапазона 500-800м из сценария, без разбивки по категориям).
- **Ссылки Яндекс.Карт — координаты берём из нескольких query-параметров, не
  только `ll=`.** Изначально парсили один `ll=`, но на живом тесте выяснилось,
  что кнопка "Поделиться" в мобильных Картах отдаёт ссылку вида
  `?text=55.778369,37.699484` — вообще без `ll=`. Порядок координат при этом
  РАЗНЫЙ: `ll=` и `whatshere[point]=` это `lon,lat`, а `text=` — `lat,lon`.
  Парсер (`bot/services/maps_link.py`) перебирает параметры по приоритету
  `ll` → `whatshere[point]` → `text` и валидирует диапазоны, поэтому `text=`
  с обычным адресом (`text=Москва, Тверская 1`) корректно даёт "координат нет",
  а не мусор. Если координаты есть уже в исходной ссылке — сетевой запрос за
  редиректом не делаем вовсе. Ссылки на организацию (`oid=`) в подавляющем
  большинстве случаев тоже несут `ll=` — этого достаточно. Юридически
  совместимого способа получить координаты по чистому `oid=` без координат не
  нашли (Search API платный, скрапинг страницы организации — то же нарушение
  ToS, что и скрапинг карт, отказались ещё на этапе архитектуры). Такие
  ссылки — исключение, необработанный edge case.
- **Ссылку вытаскиваем регуляркой из текста сообщения, не берём `message.text`
  целиком.** Тот же живой тест: при шэринге места Telegram присылает
  многострочное сообщение "адрес \ город \ ссылка", и мы скармливали в HTTP-клиент
  всю эту строку. В логах это выглядело как percent-encoded каша вместо URL.
  Если ссылки в сообщении нет вообще — отвечаем "не вижу ссылки", а не гоняем
  три ретрая до общей ошибки.
- **Определение города — по `kind="locality"` в ответе Geocoder, не `"province"`.**
  Наступили на грабли: у `"province"` в ответе Яндекса может быть ДВА разных
  значения одновременно (федеральный округ и сам город Москва как субъект),
  и первое по порядку — федеральный округ, а не город. `"locality"` даёт
  однозначно "Москва".
- **GigaChat: реальный хост `gigachat.devices.sberbank.ru`, не `api.giga.chat`.**
  Домен из части документации отвечает 404 "No such model" на бесплатном
  физлицо-ключе; рабочий вариант нашли эмпирически, проверив оба.
- **GigaChat: TLS-проверка отключена (`ssl=False`).** Известная особенность —
  сертификат выпущен НУЦ Минцифры и не всегда есть в доверенных корневых
  сертификатах ОС. Осознанный компромисс для MVP, а не забытая настройка —
  см. `bot/services/llm.py`. Если станет критично, вариант на будущее —
  установить корневой сертификат Минцифры на VPS и вернуть проверку.

## Сценарий (FSM) — цепочка состояний

```
/start (или кнопка "🏠 Начать" — постоянная reply-кнопка, показывается с первым
        сообщением; плюс сам /start есть в нативном меню команд Telegram)
  → приветствие с кратким описанием, что делает бот
START
  → WAITING_LINK          (ждём ссылку на Яндекс.Карты)
  → [автоматически, без участия пользователя]:
      - раскрыть короткую ссылку → координаты
      - Geocoder → адрес
      - Overpass → метро/транспорт и школы/садики в радиусе ~500-800м
      - сообщение пользователю "Изучаю район... 🔍"
  → WAITING_TYPE           (кнопки: квартира / дом / коммерция)
  → WAITING_ROOMS          (кнопки: студия / 1 / 2 / 3 / 4+)
  → WAITING_AREA           (текст: площадь, м²)
  → WAITING_FLOOR          (текст: этаж / этажность дома)
  → WAITING_RENOVATION     (кнопки: черновая / косметический / евро / дизайнерский)
  → WAITING_WISHES         (опционально, текст ИЛИ кнопка "Пропустить":
                             свободные пожелания риелтора одной строкой)
  → GENERATING             (собираем всё → промпт в GigaChat → текст объявления)
  → RESULT                 (кнопки: "Сгенерировать заново" / "Начать заново")
```

## Деплой

Вручную по SSH на VPS (без CI, см. архитектурные решения):

```
git pull
docker compose up -d --build
```

`.env` на сервере создаётся один раз вручную (не в git, см. `.gitignore`) на основе
`.env.example`. Логи — `docker compose logs -f`.

## Известные подводные камни

- Ссылки Яндекс.Карт бывают разных форматов: короткие (нужно раскрывать редиректом),
  длинные с координатами в `ll=`, мобильный шэринг с `text=lat,lon`, ссылки на
  организацию с `oid=`. Помнить про разный порядок координат в `ll=` (`lon,lat`)
  и `text=` (`lat,lon`) — при путанице точка уезжает за тысячи км, и проверка
  "только Москва" отклоняет валидный московский адрес.
- Overpass API может быть медленным/нестабильным на публичных инстансах — учитывать
  таймауты и, возможно, retry.
- Площадь и этаж — свободный текст, а не кнопки (числовые значения плохо ложатся
  на дискретные кнопки без огрубления данных).
- POI-сводка передаётся в LLM как структурированные факты (объект + расстояние),
  а не как готовый текст — чтобы модель не фантазировала о несуществующих объектах.
